# 好好吃饭统一账号部署与验收

核对日期：2026-10-16。状态：配置中。目标是保留 PostgreSQL、Redis 和离线能力，提供无需注册的厨房体验，以及明确授权的统一账号家庭空间；不自动绑定旧演示家庭。

## 身份与家庭权限

匿名访问者可直接开始游客体验，使用推荐、菜谱、冰箱、采购和记录。游客厨房由 HttpOnly Cookie 识别，没有独立账号密码。已有 Fribench 登录态自动识别；账号创建的厨房持久归本人，已加入家庭在新设备自动恢复，不再输入家庭登录口令。旧家庭名称和共享口令入口仅作兼容，不自动绑定到当前账号。

一个家庭可以有所有者与成员。只有所有者可以生成邀请、修改家庭设置和重置数据；成员可协作处理菜谱、库存和采购。邀请为独立随机口令，只保存摘要，7 天有效、最多加入 10 位家人。没有邀请的新账号不获得其他家庭数据。多个家庭的当前选择仍需服务端成员关系验证。

## 游客认领与离线数据

每账号在本服务仅可认领一次游客厨房。界面先同步原游客空间的离线队列，再显示预览；预览或取消不扣次数，已有账号家庭拒绝覆盖。确认将家庭成员关系、选择、唯一认领事实和游客会话失效写入同一 PostgreSQL 事务。签名预览绑定账号、家庭纪元、版本和有效期；失败不消耗机会，重复确认幂等。正常账号保存不受此次数限制。

离线快照和队列按账号及家庭双重隔离。账号切换重建界面，旧异步响应不能写回新空间。队列只删除已确认的旧序号，保留同步过程中刚加入的离线操作；重试使用原 UUID 回执。游客在认领期间的写操作会在家庭行锁内复核游客能力，避免旧会话在认领后修改账号数据。Service Worker 不缓存 API、账号路由或回调。

## 数据库和发布

继续使用本应用现有独立 PostgreSQL 与 Redis，不修改其他服务数据库，不新建重复平台数据库。`0002_spooky_nocturne.sql` 是可审查的增量迁移，新增成员、选择、邀请、认领事实及游客标记；旧家庭默认不是新游客厨房。迁移用户与运行用户继续分离，运行容器不获得数据库 owner 口令。

私有运维仓库登记 `pick-meal-well` 客户端与同源 Nginx 路由。独立身份密钥只保存在 `/etc/fribench/apps/pick-meal-well/app.env`；原数据库与 Redis Secret 路径、GID 和数据卷保留。Compose 使用完整提交设置 `PMW_VERSION`，分别固定 app 与 migrator 镜像；只执行该应用迁移和 app 更新，不重启 PostgreSQL、Redis 或 work。正式 Cookie 强制 Secure，写来源固定 `https://meal.fribench.cn`。

Node 24.21、Next.js 16.4.2 与修复后的 PostCSS/sharp 用于正式构建。生产依赖审计为 0；开发工具链仍有来自未发布修复版 braces 的上游审计提示，限于 ESLint 静态仓库 glob 输入，不进入正式运行依赖。禁止用降级生产框架或 `audit fix --force` 绕过检查。

## 验证

提交前 `npm run verify`。`TEST_DATABASE_URL` 必须指向隔离测试 PostgreSQL，认领测试只创建自己的随机 schema；`tests/next-account.integration.mjs` 只允许指定临时数据库，使用合成身份端点验证游客创建、认领、二设备恢复、邀请与所有者权限，不连接真实账号。浏览器验收包括游客推荐、记录保存、我的页面、账号入口和 390px 手机布局。

现有定时 PostgreSQL 备份仍适用新增业务表。迁移前先备份，迁移后做逻辑恢复检查；Redis 不是事实源。按用户决定不保留无引用的回滚镜像，需要恢复代码时按已推送提交重新构建，不删除业务卷。
